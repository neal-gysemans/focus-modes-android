Focus Modes for Android

Recreating iPhone Focus modes as a third-party Android app: what the platform genuinely supports, what needs a workaround, what is impossible — every claim verified against current Android docs, AOSP source, and Play policy (September 2026).

Xiaomi 17T Pro · HyperOS 3 (Android 16→17) OnePlus Nord 3 · OxygenOS 16 (final) Kotlin · Compose · target SDK 36

Verdict in six lines

  • Your zen-rule architecture is correct and doc-confirmed — one AutomaticZenRule per mode with ZenPolicy + ZenDeviceEffects, toggled via setAutomaticZenRuleState, is not just the best path but the only path for apps targeting Android 15+.
  • Per-app allowlists have no native API. The notification-relay workaround (listener + your own DND-bypass channel) is viable and is the app's differentiator — spike-gated (spike #3) because it is the fragile piece on HyperOS; allowed people never depend on it.
  • Three iOS features degrade: arbitrary per-contact allowlists (Android only knows starred/contacts/anyone), wallpaper restore (reading the current wallpaper throws on Android 14+), and a tamper-proof ongoing notification (dismissable since 14).
  • HyperOS is the real risk surface, not the SDK: Xiaomi ships its own DND UI (your modes likely have no system management screen there), silently unbinds notification listeners, and gates everything behind Autostart + battery "No restrictions".
  • Play is survivable if you choose the low-risk lane: no accessibility service, no QUERY_ALL_PACKAGES, no USE_EXACT_ALARM, defer background location. DND access, notification access, usage access, and overlays are all un-restricted today.
  • Locked scope (2026-09-30): minSdk 35, MVP = one great tile + 3 modes, manual activation + schedule triggers, starred contacts as the people allowlist. Everything else — relay, Bluetooth/geofence/Wi-Fi/calendar/app-launch triggers, blocking, wallpaper swap — deferred or spike-gated. Full decision log in §11.

§2The zen-rule engine — nuances that will bite

These four behaviors are doc/AOSP-verified and each one, missed, produces a "works on my machine, then mysteriously stops" bug:

  • User edits freeze your rule, silently. Once the user modifies an app-owned mode in Settings (any field), updateAutomaticZenRule silently discards all your changes except the rule name — no exception. Delete + re-add with the same condition does not escape: the system restores the user's customizations from a deleted-rule cache. Treat rules as write-once; read state back instead of assuming. Defuse: Room is the source of truth and the system rule is a cache — on every apply, read back getAutomaticZenRule, diff against desired, and when frozen show a "managed in system settings" badge deep-linking to ACTION_AUTOMATIC_ZEN_RULE_SETTINGS. On HyperOS (no Modes UI) the freeze likely cannot even occur.
  • Manual deactivation snoozes your rule. After the user turns a mode off manually, your STATE_TRUE is ignored until you send STATE_FALSE first — unless the Condition carries Condition.SOURCE_USER_ACTION (API 35), which always applies. Rule: tile/app toggles → SOURCE_USER_ACTION; schedules → SOURCE_SCHEDULE; geofence/BT → SOURCE_CONTEXT. Defuse: one ZenAdapter chokepoint; every call site declares its source, and the mapping is unit-tested. For schedules we deliberately accept the snooze for the current cycle (the user said no — fighting them is wrong UX and matches iOS) and send STATE_FALSE at cycle end so the next cycle re-arms cleanly.
  • A rule needs an owner. addAutomaticZenRule throws unless the rule has a ConditionProviderService or — the modern path — a configuration activity handling ACTION_AUTOMATIC_ZEN_RULE. Budget one such activity per app. Defuse: ship it from day one — it doubles as the mode editor.
  • Pure-effect modes exist. A rule with INTERRUPTION_FILTER_ALL filters nothing but still applies ZenDeviceEffects — so "Reading mode = greyscale only, all notifications through" is a first-class citizen.

The umbrella mitigation is a reconciliation loop, not event-perfect plumbing. ModeEngine never assumes a past event succeeded: on every wake — alarm fire, boot, tile tap, app open — it recomputes the desired mode from the wall clock and trigger state, reads the actual zen-rule state back, and converges the two idempotently. A missed alarm or a killed process then heals at the next wake instead of leaving the wrong mode active all day. This desired-vs-actual model is what makes the app survivable on an unreliable substrate, which is exactly what HyperOS is.

Conflict semantics with the user's own DND: when multiple rules/modes are active (including the system's), the platform combines them most-restrictive-wins per policy field (readable via getConsolidatedNotificationPolicy()). Practical consequence for the app: enforce a single-active-mode invariant — activating a mode sends STATE_FALSE to all others — so the device state stays predictable. Also note DND access cannot be granted on work profiles.

Priority rules when triggers overlap

Proposed policy (app-level, since the OS would otherwise just intersect policies):

  1. Manual always wins and pins the mode until manually cleared or its own end-condition fires.
  2. Contextual triggers (geofence, Bluetooth, app-launch, calendar) beat schedules; among contextual, most-recently-triggered wins.
  3. When the winning mode ends, re-evaluate every trigger predicate and activate the highest-priority mode still true (schedules re-assert themselves this way after a temporary override).
  4. Expose an optional per-mode priority integer later only if real conflicts show up in use.

§3Per-app allowlist: the relay mechanism

The direct answer to "can allowed apps reliably break through DND?"

Not natively — ZenPolicy filters by people, categories, conversations, and channel-bypass only. The viable mechanism, used with DND access granted:

  1. Create one notification channel owned by your app with NotificationChannel.setBypassDnd(true) — allowed because you hold DND access, but only until the user edits that channel's settings, after which the bypass flag is frozen to whatever it was.
  2. Set ZenPolicy.allowPriorityChannels(true) on your modes (API 35 default behavior otherwise controlled by the user's mode settings).
  3. In onNotificationPosted, when the source package is on the active mode's allowlist, re-post a summary through the bypass channel, reusing the original's contentIntent (a PendingIntent is a token — tapping your relay opens the original app's target).

Latency: effectively instant — the listener is called synchronously on post. Sound/vibration: comes from your channel's sound settings, not the source app's — a per-mode or per-source-app sound is configurable, but it will never be "WhatsApp's exact tone" unless the user picks it. Attribution: the relay visibly comes from your app (small icon, app name); Play's system-functionality policy requires keeping that honest — don't pixel-perfect impersonate the source notification.

Fragility budget (this is why the feature is spike-gated): HyperOS 3 is documented to silently unbind notification listeners while Settings still shows access as granted (the HyperBridge project shipped a reconnect-watchdog specifically for this). The relay therefore needs: an onListenerDisconnected → requestRebind watchdog, a staleness canary (e.g. periodic self-notification check), and a visible "relay is down, tap to fix" state. Heads-up display of the relay on HyperOS additionally depends on the per-app "Floating notifications" toggle.

Blast-radius design: the relay is post-MVP and per-mode opt-in; calls and messages from starred people break through via system-enforced ZenPolicy, never via the relay — so a dead listener degrades only the app-allowlist extra, not the critical people channel. When the watchdog detects a down relay, it says so loudly (through the bypass channel itself and the health screen) rather than failing silent.

Also worth knowing: MessagingStyle conversations, direct-reply actions, and grouped messages can be partially reconstructed (original Notification.actions carry reusable PendingIntents, including RemoteInputs) — how much survives relaying is part of the spike.

§5The tile is the product

Day to day, the Quick Settings tile is the app. iOS Control Center is the bar; this is the interaction contract the implementation is held to.

  • Tap acts, never asks. Off → activate the last-used mode with an optimistic tile flip; on → deactivate. Budget: tile visually flips in <100 ms; DND verified active in <500 ms (measured in spike #2). The dialog picker appears only when there is genuine ambiguity — no last-used mode, or the user opted into "always ask".
  • Long-press = the iOS expand gesture. The exported QS_TILE_PREFERENCES activity opens as a fast, focused mode picker with an entry into full settings — not a generic settings dump.
  • Truthful state, always. Subtitle shows the active mode's name (Tile.setSubtitle, API 30); the tile glyph swaps to the active mode's icon (monochrome — mode colour lives in-app). State is confirmed via the rule-status broadcasts + requestListeningState, so the tile is never stale after the mode changes from any other surface (schedule, app, system).
  • Locked device: toggling works from the lock screen (nothing sensitive shown); the picker goes through unlockAndRun.
  • Feedback: subtle confirmation haptic on toggle; the ongoing notification updates in the same beat so shade and tile always agree.
  • Implementation watch-outs: showDialog takes a classic Dialog from a service context — hosting Compose there needs manual lifecycle-owner wiring (spike #2 decides Compose-in-dialog vs a hand-crafted View dialog); activity launches use startActivityAndCollapse(PendingIntent) only; on HyperOS, expect the manual add-tile path (§6).
  • Per-mode tiles: deferred — the component-toggle pattern loses shade position and clutters the picker; revisit only if one-tap-per-mode proves necessary in daily use.

§6HyperOS & OxygenOS playbook

The OEM layer is where this app lives or dies. Everything below is community/vendor-verified, not SDK-documented.

How your modes will look on each device

  • HyperOS (17T Pro): Xiaomi ships its own DND UI and there is no evidence the AOSP Modes settings screen exists on HyperOS 3 — your zen rules will likely work via API but have no system management surface; your app is the only UI. Xiaomi's own DND layer has documented bugs (random self-activation, schedules not releasing). Spike #1 verifies a third-party rule actually silences Xiaomi's notification pipeline. Note your 17T Pro is receiving stable Android 17 (HyperOS 3.3) right now — test on both bases.
  • OxygenOS 16 (Nord 3, final update): near-stock DND/Modes surfaces; the risk here is process death, not API divergence.

Onboarding checklist the app must walk users through

  1. Xiaomi: Autostart (Security app) and battery "No restrictions" — two independent gates, both required, neither requestable via API (the MIUI-autostart library can only detect). Lock the app in recents (may not survive reboot). "Other permissions" → "Display pop-up windows while running in background" if any trigger ever launches UI. "Floating notifications" enabled for the app so relayed notifications banner. Last resort: disable MIUI optimization.
  2. OnePlus: Battery → "Don't optimize", disable Sleep standby optimization and auto-launch management — and warn users that OxygenOS randomly reverts the exemption, so ship a recurring health-check screen (re-verify listener bound, alarm fired on time, exemption still set), not a one-time wizard.
  3. Both: DND-access grant screens have historically been buried/hidden on Xiaomi — handle the settings intent failing and provide manual navigation instructions.

Quick Settings on HyperOS

Third-party tiles appear but are buried at the end of the control-center edit list; the first four toggle slots are locked. requestAddTileService is unverified on HyperOS (works on AOSP-close ROMs; auto-denies after repeated refusals everywhere) — always ship the manual "Edit control center → scroll down" instruction as fallback. Expect exact alarms to drift 1–2 minutes on Xiaomi even when whitelisted; treat that as acceptable for mode switching.

Data model

  • Mode: id, name, iconKey, colour, zenRuleId (nullable until registered), interruption policy (people level for calls/messages, repeat callers, conversations), effects (greyscale, dimWallpaper, nightMode), wallpaperHome/Lock (imported file refs, nullable), allowedApps [pkg], blockedApps [pkg].
  • Trigger: id, modeId, type (SCHEDULE | BLUETOOTH | GEOFENCE | CALENDAR | WIFI | APP_LAUNCH), typed params (serialized), enabled.
  • ActiveState (DataStore, single source of truth): activeModeId, activationSource, since, pinnedByUser.

Key invariants: every entry point (tile tap, receiver, boot) funnels a TriggerEvent into ModeEngine — nothing toggles a zen rule directly; ModeEngine's apply step is idempotent and reads back actual rule state (because user edits can freeze rules, §2); boot receiver re-plants alarms (and, if triggers return later, geofences), never starts an FGS (Android 15 restricts BOOT_COMPLETED FGS types).

§9MVP — smallest version worth using daily

  • 3 seed modes (Work, Sleep, Personal), editable: name, icon, colour, people policy (starred / contacts / anyone + repeat callers), device effects (greyscale, dim wallpaper, dark theme).
  • Manual activation as the primary flow — the tile per the §5 contract, in-app toggles, and setManualInvocationAllowed(true) so modes are toggleable from any surface the OS offers.
  • Schedule triggers, backed by the reconciliation loop (§2) so a missed alarm self-heals.
  • Starred-contacts guidance: an onboarding card that says plainly "people allowed through = your starred contacts", shows the current starred list (optional READ_CONTACTS — the feature works without it), and one-tap opens the Contacts app to star someone. Repeat-callers on by default (iOS parity: a second call within minutes is probably urgent).
  • Ongoing notification with "turn off" action (informational — dismissable since Android 14).
  • Setup & health screen: DND access, exact-alarm grant, Xiaomi/OnePlus checklist, and a recurring health check (OxygenOS reverts exemptions; HyperOS unbinds listeners).
  • minSdk 35, targetSdk 36, no INTERNET permission.

Explicitly out of MVP: per-app allowlist relay (gated on spike #3), all context triggers (Bluetooth, geofence, Wi-Fi, calendar, app-launch), app blocking, wallpaper swap (dropped for now), per-mode tiles.

§10Technical spikes, in order

Reordered after the scope decisions: the MVP-critical spikes come first; the relay spike now gates a post-MVP feature rather than blocking the start.

1 · Zen rules on HyperOS existential

Create/activate a rule with policy + effects; verify Xiaomi's pipeline actually silences; find the DND-access grant screen; test SOURCE_USER_ACTION vs snooze-override; check whether any Modes management UI exists on HyperOS 3/3.3 (Android 16 and 17 bases).

Exit: a mode toggled from code demonstrably filters notifications and applies greyscale/dark on HyperOS. If this fails, the whole approach is renegotiated — nothing else matters until it passes.

2 · Tile feel MVP-critical

The §5 contract, measured: requestAddTileService on HyperOS, optimistic-flip latency, tap-to-DND-active timing, showDialog picker (Compose-in-dialog vs View dialog), long-press preferences activity, locked-device behavior, subtitle/icon updates from external state changes.

Exit: tap-to-active measured <500 ms on both devices; documented add-tile path per device; a picker that feels instant.

3 · Notification relay breakthrough gates the allowlist feature

NLS + setBypassDnd channel on 17T Pro and Nord 3: does the relay sound/vibrate/head-up under an active mode; latency; RemoteInput reply survival; behavior after user edits the channel; HyperOS listener-unbind watchdog.

Exit: relayed WhatsApp message audibly breaks through DND on both devices within 2 s, and the watchdog detects a forced unbind. Kills or confirms the future flagship feature.

4 · Schedule reliability & process death

Exact-alarm drift on HyperOS with/without Autostart + No-restrictions; boot re-registration; force-stop/swipe-away matrix; Nord 3 exemption-revert behavior; verify the reconciliation loop heals a deliberately missed alarm.

Exit: measured worst-case drift table + minimum required setup per device, feeding the onboarding copy verbatim.
